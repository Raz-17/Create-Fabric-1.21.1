# Create for Minecraft 1.21.1 Fabric

Review date: 2026-10-30

## Executive conclusion

There is no official, supported Create Fabric 1.21.1 release in the reviewed
repositories.

The Fabricators of Create repository does contain a substantial
`mc1.21.1/fabric/dev` source branch, but it is a development snapshot, has no
published release, and its current source build does not configure successfully
in a clean checkout. The maintainer discussion also states that 1.21.1 is not
planned for an official quality release without substantial further work.

The jar in this repository is a separate third-party build:

- Fabric mod id: `create`
- Version: `6.0.9-fabric.1.5.2-cowsedit`
- Main classes: `com.acowsays.create.*`
- Minecraft range in `fabric.mod.json`: `>=1.21.1 <1.21.2`
- Java requirement in `fabric.mod.json`: `>=21`
- SHA-256: `BC1A91F93C52E83AAB23CF25F0F9E3B7B40FEEA8A9747BAED81360D5C7ABF064`
- Size: 18,863,849 bytes

That jar may be usable on a 1.21.1 Fabric server, but it must be treated as an
unofficial, unverified build rather than as an artifact produced by the
Fabricators repository. It should be tested in a copy of the server and world
before being used on the live server.

## EMI recipe diagnosis

The supplied mod list includes:

- `emi-1.1.24+1.21.1+fabric.jar`
- `RoughlyEnoughItems-16.0.799-fabric.jar`
- `fabric-api-0.116.14+1.21.1.jar`
- `sodium-fabric-0.8.12+mc1.21.1.jar`
- `iris-fabric-1.8.14-beta.1+mc1.21.1.jar`

The supplied Create jar's `fabric.mod.json` registers `rei_client` and
`rei_common` entrypoints, but it does **not** register an `emi` entrypoint and
does not declare EMI as a dependency. This directly explains why EMI does not
show Create's processing recipes. Installing EMI alone cannot provide those
recipes; Create must ship an EMI plugin that registers its categories and
recipe adapters.

The Fabric source branch already contains a substantial EMI implementation:
`com.simibubi.create.compat.emi.CreateEmiPlugin` plus its recipe and rendering
classes. It registers categories for milling, crushing, pressing, fan
processing, mixing, packing, sawing, deploying, sequenced assembly, spouting,
and other Create processing types. This is strong evidence that the desired
feature should be restored from that implementation rather than written from
scratch.

However, copying the source plugin into the supplied jar is not a one-line
metadata change. The plugin references the source branch's `com.simibubi`
classes, recipe model, transfer implementation, and registry names, whereas
the supplied jar uses `com.acowsays` classes and custom infrastructure. The
plugin and all of its dependent classes must be ported as a coherent unit and
compiled against the exact custom jar source. A fabricated `emi` entrypoint
would only cause a class-loading crash or silently fail.

## Repositories reviewed

### Official Create

Repository: <https://github.com/Creators-of-Create/Create>

- The repository default branch is `mc1.21.1/dev`.
- It has official 1.21.1 releases, including `mc1.21.1-6.0.10`.
- This repository is the upstream multi-loader/Forge-side project, not a
  Fabric release source. An official Create 6.0.10 jar should not be placed in
  a Fabric server unless its metadata explicitly identifies Fabric.
- The upstream repository is active, but its issue count and release activity
  do not imply Fabric support.

### Fabric port

Repository: <https://github.com/Fabricators-of-Create/Create>

- Default branch: `mc1.20.1/fabric/dev`.
- 1.21.1 branch: `mc1.21.1/fabric/dev`.
- The 1.21.1 branch currently points to commit
  `7f1f67b6ecbbde512e8d35404f3621a6875ce838` (`porty mcport`, 2025-03-11).
- No GitHub release is published for the Fabric 1.21.1 branch.
- The branch contains a complete Gradle source tree and Fabric metadata, so it
  is a real porting effort and not merely an empty placeholder.
- Its `DIFFERENCES.md` documents behavior differences from Forge, including
  hose-pulley capacity and fluid/display-link behavior.

- [Fabric issue #1905](https://github.com/Fabricators-of-Create/Create/issues/1905)

- [Fabric PR #1876](https://github.com/Fabricators-of-Create/Create/pull/1876)
  is an “Initial upload” PR targeting the same 1.21.1 branch. It was closed
  without being merged.

The maintainer response in issue #1849 is the most important evidence:

> 1.21.1 is old now, and I don't want to develop on it anymore.

The same response says that an unofficial approach could merge the Forge code,
update Porting Lib, and patch remaining issues, but that this would not meet
the maintainer's desired quality bar. It also says Porting Lib would need to be
replaced before an official release. Therefore, the branch should not be
assumed to have the same stability or compatibility guarantees as a release.

## Reproducible source-build result

I checked out the Fabric branch at
`7f1f67b6ecbbde512e8d35404f3621a6875ce838` and ran:

```text
gradlew.bat build --no-daemon
```

Result: **failed during Gradle configuration before compilation**.

The configured Maven repository could not resolve these compile-only
compatibility artifacts:

```text
dev.ftb.mods:ftb-chunks-fabric:2001.3.1
dev.ftb.mods:ftb-teams-fabric:2001.3.0
dev.ftb.mods:ftb-library-fabric:2001.2.4
```

The failure is not proof that all source code is uncompilable; it is proof that
the checked-out branch is not currently reproducible with its committed build
configuration. Removing or replacing those optional declarations may allow
the build to proceed, but that would be a source change requiring a full build,
client test, server test, and modpack compatibility test.

The branch also uses older 1.21.1-era versions of Fabric Loader, Fabric API,
Flywheel, Ponder, Registrate, Porting Lib, and related libraries. Those exact
versions must be kept together; independently updating them is likely to create
runtime incompatibilities.

## Assessment of the supplied jar

The supplied jar is not a direct build of the Fabricators source branch:

- The source branch uses `com.simibubi.create.*`.
- The jar uses `com.acowsays.create.*`.
- The jar declares the custom version `6.0.9-fabric.1.5.2-cowsedit`.
- The jar contains custom entrypoints and custom injected interfaces.
- Its metadata declares Minecraft 1.21.1 and Java 21 compatibility.
- Its metadata does not provide the same dependency declarations as the source
  branch, so the complete dependency provenance cannot be inferred from the
  jar alone.

This makes the jar the most practical starting point for the requested
modpack, but also means that bug reports should be directed to the author of
that build, not automatically to either upstream repository.

## Recommended server path

1. Make a backup of the server and world.
2. Create a disposable 1.21.1 Fabric test instance using Java 21.
3. Install the exact Fabric Loader range accepted by the jar and a matching
   Fabric API/modpack dependency set.
4. Install the supplied Create jar only; do not also install a Forge/NeoForge
   Create jar or another Fabric jar with mod id `create`.
5. Start the server and inspect `logs/latest.log` for missing dependencies,
   mixin failures, registry errors, or crashes.
6. Join with a client containing the same Create jar and compatible versions of
   every Create addon. Test world creation, joining, item/block registration,
   contraptions, trains, chunk boundaries, save/reload, and a clean server
   restart.
7. Only after those tests pass should the jar be introduced to the live server.

Create addons built for another Create/Fabric/Minecraft version should be
considered incompatible until individually verified. In particular, do not
assume that addons for the official Forge Create 6.x release work with this
custom Fabric build.

## What is still needed for a reliable go/no-go decision

The complete modpack list is needed, including exact filenames or versions for
Fabric Loader, Fabric API, Create addons, Sodium/Iris, REI/EMI/JEI, optimization
mods, chunk-claim mods, and any server-only mods. The next practical validation
step is to run the supplied jar in an isolated copy of that exact pack and
capture the first startup log and any crash report.

Until that test is completed, the accurate status is:

**Technically plausible for a private 1.21.1 Fabric server using the supplied
unofficial jar; not an officially supported or reproducibly source-built
Create Fabric 1.21.1 release.**

## Recommended development strategy

The best strategy is staged rather than immediately merging all upstream
changes:

1. **Restore EMI first.** Obtain the source corresponding to the
   `com.acowsays` jar, port the Fabric branch's EMI plugin and dependent recipe
   adapters, add the `emi` entrypoint, and build a new jar. Validate that EMI
   displays Create machine recipes before changing gameplay code.
2. **Make the 1.21.1 source build reproducible.** Remove or correctly replace
   the unavailable optional FTB compile-only dependencies, without changing
   runtime behavior, then build the unmodified Fabric branch successfully.
3. **Compare behavior and APIs.** Establish tests for registration, recipes,
   contraptions, trains, fluids, saves, and server startup. This prevents
   upstream changes from hiding regressions behind the EMI work.
4. **Forward-port selectively.** Bring upstream Create changes over by feature
   or commit, adapting them to Fabric and the port's mappings. Do not merge the
   official Forge branch wholesale: it uses different loader APIs, rendering,
   transfer systems, mixins, and registries.
5. **Publish only tested builds.** Keep the original jar and each rebuilt jar
   separately identifiable, and test the exact client/server mod set.

The mod list also contains both EMI and REI. That is acceptable in principle,
but the first milestone should target EMI because it is the missing integration.
The server's Fabric Loader `0.20.1` is above the supplied jar's declared
minimum `0.17.2`; the more important compatibility risks are the custom Create
build, its hidden/included dependencies, and Create addon versions.

## Public-port work started

A personal fork has been created at
<https://github.com/Raz-17/Create>, and the public Fabric repository is cloned
at [Create-fabric](B:/Github/Create-fabric). The local working branch is
`work/mc1.21.1-fabric`.

The first build repair removes the unavailable FTB Chunks/FTB Library
compile-time compatibility layer because those mods are not in the supplied
modpack. It also removes the associated optional client hooks and mixin
accessors. This is intentionally narrower than deleting all compatibility
support.

After that repair, Gradle reaches Java compilation but the branch exposes a
larger porting baseline:

- `AllAttachmentTypes.java` still imports NeoForge attachment and registry
  classes.
- Many classes import NeoForge APIs.
- Many classes import `io.github.fabricators_of_create.porting_lib.*`, but
  Porting Lib is not declared in the branch's Gradle dependencies.
- The source contains 52 files with NeoForge or Forge imports.

Therefore the 1.21.1 branch is not currently a buildable Fabric implementation;
it is a partially merged/mixed-loader development snapshot. The next work is a
real Fabric porting phase: establish the matching Porting Lib 1.21.1 modules,
remove or replace loader-specific source paths, and compile in small subsystem
batches. EMI should be restored after that baseline compiles, because its
existing implementation depends on the same recipe, registry, and transfer
APIs that are currently unresolved.
